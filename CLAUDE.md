



# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SecondBrain is a study notes summarizer. Users add sources — PDFs, PPTs, YouTube video links and website links — and the app turns them into concise notes that cite where each point came from (for YouTube, the timestamp in the video), generates flashcards for quick revision, and has an AI assistant that answers questions from the saved material. `backend/` is FastAPI + Postgres + Chroma; `frontend/` is React 19 + Vite + TypeScript + Tailwind v4.

Current gaps against that goal (as of 2026-09):
- **Word sources carry no location.** `.docx` has no pages (only Word's layout makes them); the nearest heading would be the only option. PDFs uploaded before page tracking also cite nothing until re-indexed (`scripts/reindex_pdf_pages.py`).
- **PowerPoint search results have no slide number** (a matched chunk that starts mid-slide doesn't contain its marker); summaries and flashcards do cite slides.

**PDF page citations:** `PDFService.extract_pages` → `RAGService.chunk_pages` (same packing as `chunk_text` via the shared `_pack`, but each sentence carries its page) → `chunks.page_start` / `page_end` and the same keys in Chroma metadata. Pages are physical PDF pages, not printed page labels; a chunk crossing a page break (or carrying overlap from the previous page) spans two. `format_pages` renders "p. 12" / "pp. 12–13". PDFs uploaded before this have null pages and behave as before; `scripts/reindex_pdf_pages.py` (dry run by default, `--apply`) rebuilds their chunks and vectors from `uploads/` with backup/rollback, leaving summaries and flashcards as they are. Offline tests: `tests/test_pdf_page_citations.py`.

**Flashcard citations:** `generate_cited_flashcards` (`app/services/ai/flashcard_service.py`) works from the stored chunks, labelled `[S0]`, `[S1]`, …; the LLM returns a `source` label per card, validated against the batch it was shown (anything else → no citation, card kept). `build_chunk_citations` turns a chunk into a citation from stored data: YouTube `("02:05", timestamp url)`, website `(page title, url)`, PPTX `("Slides 3–4", None)` from `[Slide N]` markers tracked across chunks, PDF `("p. 12", None)` from the chunk's stored page range, DOCX `None`. Saved on `flashcards.source_label` / `source_url` at generation time; old cards stay null until regenerated. Coverage is enforced in code, not the prompt (the model favours the start of whatever it sees): short sources are split into `ceil(count/3)` consecutive groups, long ones sampled evenly, picks taken round-robin and returned in source order. Documents without chunks fall back to `generate_flashcards(doc.content)`. Offline tests: `tests/test_flashcard_citations.py`.

**Summary citations:** `generate_cited_summary` (`app/services/ai/summary_service.py`) labels each stored chunk `[S0]`, `[S1]`, … and the LLM cites labels, never times, pages or slides; `replace_labels` then swaps each label for that chunk's citation (from `build_chunk_citations`): `[mm:ss](url&t=…)` links for YouTube (`generate_youtube_summary` is a wrapper), "(p. 12)" for PDFs with page ranges, "(Slide 4)" for PowerPoint; several plain citations on one point merge into "(p. 3; pp. 7–8)". Labels matching no chunk (or a chunk without a citation) are dropped. Markdown-escaped labels (`\[S3\]`, which some models write) are matched and replaced too, and so are ranges (`[S0-S3]`, any dash, `S` optional after it), which expand to every chunk in between, clipped to the last chunk; `CITATION_RULE` also forbids ranges and labels written as words ("S2 and S3"). Keep it that way — don't let the model write locations. Websites, Word files and pre-page-tracking PDFs use the plain `generate_summary`. Both share `SUMMARY_SYSTEM_PROMPT`, which asks for plain-text formulas (not LaTeX) and flags only explanations the material leaves incomplete, never topics it doesn't cover; both run the result through `plain_inline_math` (strips `\(…\)`, shared with merged summaries), since the page doesn't render maths. Summaries are cached in `summaries`, so prompt changes only show after regenerating. Offline tests: `tests/test_youtube_summary_citations.py`, `tests/test_citation_label_ranges.py`, `tests/test_single_summary_formatting.py` (mocked LLM, safe to run).

**OCR (scanned PDF pages and images):** `app/services/ocr/ocr_service.py`, one OpenRouter vision call per page with its own client (120 s timeout) and model `OCR_MODEL` (default `DEFAULT_OCR_MODEL`, a `:free` model that accepts images; read at import). Calls go through `run_calls` (parallel, in order) and retry like `_complete`; failures are `AIGenerationError` via `ai_failure`, which the upload routes return as 502 "Text recognition failed: …". An empty reply means "no text on this page", not an error. `MAX_OCR_PAGES` (20) per upload, checked before any call. PDFs: `PDFService.scanned_pages` (no text, has an image; blank pages are left alone) → `render_pages` (150 dpi JPEG) → `prepare_image` → OCR text put back into `pages[n-1]`, so `chunk_pages` cites it with its physical page; `metadata_json` records `ocr_pages`, and `scripts/reindex_pdf_pages.py` skips those PDFs. Images: `POST /api/v1/upload/images` (multipart `files`, JPEG/PNG, 20 MB each, `MAX_IMAGES_TOTAL_SIZE` 50 MB together) makes **one** document, `source_type="image"`, each image a page in the order sent (`chunk_pages`, so citations are "p. 2" like PDFs; everything that treats `"pdf"` pages, i.e. `build_chunk_citations`, search `location`, the summary route, accepts `"image"` too). `prepare_image` applies EXIF rotation, flattens transparency onto white, shrinks to 2000 px and re-encodes as JPEG; originals are saved as `uploads/{file_id}.{n}.{ext}` so the delete route's `{file_id}.*` glob removes them. Frontend: `UploadZone.planUploads` sends all images picked together as one unit (`uploadImages`), and other files one per unit as before. Offline tests: `tests/test_ocr.py`.

**Website links:** `POST /api/v1/upload/website {url}` → `app/services/web/`. `url_safety.py` is the SSRF guard: only http/https on ports 80/443, and every resolved address must be public (`is_public_ip`). It runs on the submitted URL and on every redirect hop (redirects are followed by hand, max 5), and `SafeNetworkBackend` re-resolves at connect time and connects to the checked IP (stops DNS rebinding). Keep `follow_redirects=False` and `trust_env=False`, and never use trafilatura's own downloader. Limits: 5 MB, 20 s total. `WebService.extract_article` uses trafilatura for main text + title (reference lists, footnote markers and navboxes are pruned first via `_PRUNE_XPATH`; a short page whose text says "enable JavaScript" counts as JavaScript-only) and raises `WebPageError` (blocked / login_required / javascript_required / no_text / …; `.message` is user-facing, `.status_code` is the HTTP status). Stored as `source_type="website"`, `filename`=page title, `source_url`=final URL, details in `metadata_json`. Re-importing a saved page returns 409 with `detail={message, document_id}` (YouTube does the same for a saved video ID, checked before the transcript fetch; these are the only upload errors whose detail is an object, and `importError` in `api/client.ts` turns them into `DuplicateSourceError`): `url_key` in `web_service.py` defines "same page" and is compared against each website doc's `source_url` and `metadata_json.original_url`, before fetching and again after redirects. Search matches carry `source_type`/`source_url`, and website summaries get a code-built `Source: [title](url)` footer (`append_source_link`). Offline tests: `tests/test_website_ingestion.py` (network, DNS, DB and LLM all mocked, safe to run).

**Accounts:** email/password sign-up and login (`app/routes/auth.py`, `app/services/auth_service.py`, models in `app/models/user.py`). Passwords are bcrypt hashes (at least 8 characters; over 72 bytes is refused, not cut). A session is a `secrets.token_urlsafe(32)` token, 30 days; only its SHA-256 is stored in `sessions`, and logout deletes the row. The browser gets it in an HttpOnly, SameSite=Lax cookie `sb_session` (the frontend never reads it); scripts can send `Authorization: Bearer`. `get_current_user` is a parameter of **every** endpoint except `/api/v1/auth/*`, `/api/v1/health` and `/`; `tests/test_ownership.py` walks the OpenAPI schema and fails if any endpoint answers without a session. Ownership: `documents.user_id` and `merged_sets.user_id` (chunks, summaries, flashcards follow their document). Another user's document or set answers 404 exactly like a missing one (`ownership.owned_document`, `_get_set`), uploads stamp `user_id` on the document **and** its Chroma metadata, and search queries Chroma with `where={"user_id": …}`, so anything that writes Chroma metadata must keep `user_id`. Duplicate link checks are per user. Rows from before accounts have `user_id` null and are invisible until `scripts/assign_documents_to_user.py --email … [--apply]` assigns them. `ALLOW_SIGNUP=false` closes sign-up; `SESSION_COOKIE_SECURE=true` for HTTPS. Frontend: `AuthContext` (checks `/auth/me` at start-up), `RequireAuth` around the app (the splash, which loads documents, is inside it), `/login` and `/signup` (`AuthPage`); every call goes through `apiFetch` in `api/client.ts`, which fires `AUTH_EXPIRED_EVENT` on 401 so the app returns to login. Offline tests: `tests/test_auth.py`, `tests/test_ownership.py`, `tests/test_assign_documents.py`.

**Password reset:** `app/services/password_reset.py`, public endpoints `POST /api/v1/auth/password-reset/request|check|confirm` (listed as public in `test_ownership.py`). `request` answers the same 202 whether or not the email has an account and sends in a `BackgroundTasks` job, so neither the reply nor its timing reveals registered emails; at most 3 links per account per hour (extra requests get the same reply and send nothing). Tokens (`password_reset_tokens`, SHA-256 only) are single use, expire after `PASSWORD_RESET_MINUTES` (30), and a new request expires the account's earlier unused ones. `confirm` sets the bcrypt hash, marks the token used under a row lock, and deletes every session of the account. Email goes through `app/services/email_service.py`: one POST to Brevo's `https://api.brevo.com/v3/smtp/email` (`api-key` header) with httpx; failures are logged, never raised; without `BREVO_API_KEY` the whole message, link included, is written to the backend log instead. The link is `{APP_BASE_URL}/reset-password?token=…`; `ResetPasswordPage` reads the token once and removes it from the address bar. Frontend: `/forgot-password`, `/reset-password` (public routes), "Forgot password?" on the login page, shared `AuthShell` / `PasswordField`. Offline tests: `tests/test_password_reset.py` (Brevo via an httpx mock transport).

**Merged sets:** 2–8 documents of any type (at most `MERGED_MAX_CHARS`, default 300,000 characters of `Document.content` together, read at creation by `max_total_chars()`, and no single document over `MERGED_MAX_DOC_CHARS`, default 100,000, `max_doc_chars()`; the 400 names every document over it) studied as one. Both limits apply only when a set is created: existing sets keep their members and can still be regenerated. `GET /documents` returns each document's `char_count` so the frontend can mark documents over the limit (`components/library/mergeLimits.ts` mirrors the defaults; `MergePrompt` doesn't pre-select them and explains why, Library select mode greys them out), and the backend message still covers a changed `.env`: `app/routes/merged_sets.py` (`/api/v1/merged-sets`), models in `app/models/merged_set.py`, generation in `app/services/ai/merged_service.py`. They have their own tables (`merged_sets`, `merged_set_documents` with a `position`, `merged_summaries`, `merged_flashcards`) and never touch the per-document `summaries` / `flashcards`, so a set can't overwrite a document's own study material. Creating a set with exactly the documents of an existing one, in any order, returns that set with `created: false` (the page says it was reopened). Deleting a document removes its membership (ON DELETE CASCADE) and unlinks its merged cards (`document_id` SET NULL); both happen in Postgres, since `Document` has no relationship to these tables. The set then reports `summary_stale` (the summary's stored `document_ids` include a non-member) / `flashcards_stale` (an unlinked card) until regenerated, and it can't be regenerated with fewer than 2 members. Summary: `generate_merged_summary` labels every chunk of every source `[S0]…` across the set, maps long sources batch by batch without mixing two sources in a batch, and `merged_citation` puts the source's number in front of each chunk's citation: "(1: p. 12)", "(2: Slide 4)", "[3: 02:05](url)", "[4](url)" for web pages, "(5)" for Word and page-less PDFs. Plain citations are grouped by source ("(1: p. 3, pp. 5–6; 2: Slide 4)", `join_by_source`), a code-built Sources list at the top maps the numbers to documents, and sources are numbered 1..n over the current members when generated. The merged prompt asks for "Source 2" (never the labels) in sentences and plain-text formulas; `plain_inline_math` also strips `\(…\)`. Flashcards: `allocate_cards` splits the count over the sources by text size (at least 1 each, adding up exactly) and each share comes from `generate_cited_flashcards`; card labels name the source ("Graph_PPT.pdf · p. 12"). Frontend: the Library's Select mode (cards and table rows become checkboxes, sticky bar, Escape leaves) calls `createMergedSet`, and so does `MergePrompt`, which the upload area (`UploadZone`) shows after every successful upload (file, several files, YouTube, web page) when there's something to merge: the new document(s) start selected (upload order), existing ones can be ticked (from a fresh `getDocuments()`; source badge, chunk count, filter box past 6), 2–8 in total, with a warning past 150 chunks that the summary takes many AI calls. It deliberately doesn't navigate to the set (the summary page generates on open); it shows an "Open merged set" link instead. Multi-file uploads go one at a time through the normal upload endpoints (a failed or skipped file doesn't stop the rest) and a results panel lists each. `onUploadSuccess({ keepOpen: true })` tells the Library not to close the upload area while results or the prompt show, and `onMergedSetCreated` makes it reload its sets. `SummaryPage` / `FlashcardPage` take `merged` for `/library/merged/:setId/summary|flashcards`. Offline tests: `tests/test_merged_sets.py` (in-memory SQLite with foreign keys on), `test_merged_summary.py`, `test_merged_flashcards.py`.

**Spaced repetition (SM-2):** `app/services/spaced_repetition.py` (pure: `review(ease, interval_days, repetitions, grade, today)`), routes in `app/routes/review.py` (`/api/v1/review`). Both card tables carry `ease` (2.5, floor 1.3), `interval_days`, `repetitions`, `due_date`, `last_reviewed_at`, `first_reviewed_on` (`ReviewScheduleMixin` in `app/models/flashcard.py`; columns added in `init_db`), and every card dict includes them (`schedule_dict`). Grades: again = SM-2 quality 2 (starts over, due today, ease −0.32), good = 4 (1 day, 6 days, then interval × ease), easy = 5 (ease +0.1, interval × `EASY_BONUS` 1.3, always later than good). A card nobody has rated has `due_date` null and **counts as due** as a new card, but at most `NEW_CARDS_PER_DAY` (default 20; 0 turns new cards off) a day: the allowance is the limit minus cards whose `first_reviewed_on` is today, so new cards started in a deck use it up too. New cards come oldest first, after scheduled reviews; its first rating puts a card on the schedule. Regenerating a deck replaces its cards, so their schedule starts over. `POST /review/cards/{document|merged}/{card_id} {grade, today}` (row lock; another user's card is 404), `GET /review/due?today=` (cards from document and merged decks, oldest due first then today's new cards, with `deck_id` / `deck_name` / `deck_source_type`, plus `review_count`, `new_count`, `new_waiting`, `new_limit`, `new_left_today`), `GET /review/due/count?today=` (the same numbers, no cards). `today` is the browser's local date (`localToday()` in `api/client.ts`), used when within a day of the server's UTC date (`local_today`). Frontend: Again/Good/Easy (keys 1/2/3) under the flipped card in `FlashcardPage`, the `/review` "Due today" page (`DueTodayPage`, one session over all due cards; Again sends a card to the back), and a count in the sidebar (`useDueCount`, refreshed on `DUE_CHANGED_EVENT`, navigation and focus). `FlipCard` is the card both pages use; `reviewSchedule.ts` has the labels. Offline tests: `tests/test_spaced_repetition.py`.

**Quizzes:** 10 multiple-choice questions for a document or a merged set. `app/services/ai/quiz_service.py` (own client) works like cited flashcards and shares their batching (`plan_batches`, `labelled_batch`, `citation_fields`, `pick_across_batches` in `flashcard_service.py`): the model returns `question`, 4 `options`, `answer` (a letter; an index or the option text is accepted too), `explanation` and a `source` label; `parse_quiz_json` drops anything without exactly 4 distinct options and a valid answer, and `shuffle_options` reorders the options in code (models put the right one first). Documents without chunks use `generate_quiz` (chunked here, no citations); merged sets use `generate_merged_quiz` (`allocate_cards` shares, `merged_card_citation` labels, grouped by source). Tables `quizzes` (exactly one of `document_id` / `set_id`, CASCADE), `quiz_questions` (`options` JSON, `correct_index`, `explanation`, `source_label`/`source_url`, merged `document_id` SET NULL → quiz `stale`), `quiz_attempts` (`answers` JSON, null = skipped, `score`, `total`). Generating never replaces a quiz: the newest is shown and every attempt keeps its questions. Routes in `app/routes/quiz.py`: `GET|POST /api/v1/documents/{id}/quiz` and `/api/v1/merged-sets/{id}/quiz` (`?count=` 1–20, default 10) return `{quiz, attempts}` (last 20 attempts across all the owner's quizzes, newest first); `POST …/quiz/{quiz_id}/attempts {answers}` scores on the server (400 if the answers don't fit the quiz; a quiz answered through another document or set is 404). Frontend: `QuizPage` (`/library/:documentId/quiz`, `/library/merged/:setId/quiz` with `merged`) generates one on first visit like the other study pages, shows each answer's explanation and citation right away (keys 1–4 / A–D, Enter), then the score, a review and past attempts; Quiz buttons on Library cards, table rows and merged set cards. Offline tests: `tests/test_quiz.py`.
`SECOND_BRAIN_PROJECT_CONTEXT.md` holds the product/UI brief (design direction, naming rules, "don't invent endpoints or fake data"). It is partly stale — e.g. it says only PDF upload works and YouTube is "Coming Soon", but PPTX/DOCX/YouTube are implemented end to end. Trust the code over that document.

## Backend architecture

- `main.py` loads `.env`, mounts eight routers, and calls `init_db()` on startup. There is no Alembic: `init_db()` (`app/database/db.py`) runs `create_all` plus hand-written `ALTER TABLE ... IF NOT EXISTS` statements. Add new columns there as well as on the model.
- Routers live in two places: `app/api/upload.py` (all ingestion) and `app/routes/` (`documents`, `search`, `study`, `merged_sets`, `auth`, `review`, `quiz`). (`app/api/` holds nothing else.)
- **Dual storage.** Postgres holds `documents` (with full extracted text in `content`), `chunks`, `summaries` and `flashcards`. Chroma (`app/database/chroma.py`, collection `secondbrain_chunks`, cosine) holds the vectors. `Chunk.chroma_id` links the two, formatted `"{document_id}-{chunk_index}"`; Chroma metadata carries `document_id`, `filename`, `source_type`, for YouTube `source_url`/`start_seconds`, and for PDFs `page_start`/`page_end`. Anything that creates or deletes chunks must keep both stores in sync — see `_store_document_and_chunks` in `upload.py` (Chroma add then DB commit, with Chroma cleanup on failure) and `delete_document` in `routes/documents.py`. Postgres is the source of truth: on startup `rebuild_if_empty` (`app/database/chroma_rebuild.py`) re-embeds every chunk into an empty collection with the same ids and metadata as an upload (`chunk_metadata`), since the free Hugging Face Space loses `vector_db/` on every restart; keep `chunk_metadata` in step with `_store_document_and_chunks`. Offline tests: `tests/test_chroma_rebuild.py`.
- **Ingestion flow:** each upload endpoint saves to `uploads/{uuid}.{ext}` (everything after the save runs inside `_removed_on_failure`, which deletes the file if the upload fails, so no orphaned files are left; PDFs are parsed from the in-memory bytes because PyMuPDF keeps a file it failed to parse open while the error is alive, and Windows then refuses the delete; scanned pages go through OCR (see above), and `SCANNED_PDF_MESSAGE` is for when OCR finds no text) → a format service in `app/services/<fmt>/` extracts text → `RAGService.chunk_text` (sentence-packed ~800 chars, 150 overlap; PDFs use `chunk_pages`, see above) → `_store_document_and_chunks`. YouTube skips the file and uses `YouTubeService.pack_transcript_chunks` to keep per-chunk start timestamps. Website links also skip the file (fetch → extract → `chunk_text`). Code targets `youtube-transcript-api` 1.x (instance `.fetch()`).
- **Embeddings:** only through `app/services/embedding_service.py` (single cached `all-MiniLM-L6-v2`). Don't instantiate SentenceTransformer elsewhere.
- **LLM calls:** OpenRouter through the `openai` SDK with `base_url="https://openrouter.ai/api/v1"`. The model is `MODEL_NAME` in `summary_service.py` (imported by the other two): `OPENROUTER_MODEL` from `.env` if set (e.g. a `:free` model for testing), else `openai/gpt-4o-mini` (128k context, up to 16k output tokens; `DEFAULT_MODEL`); it's read at import, so changing it needs a backend restart, and a non-default model is logged at startup. Reasoning models spend part of `max_tokens` thinking, so every summary/flashcard cap adds `REASONING_ALLOWANCE` (3000); `reply_text` / `check_reply` log replies that still hit the limit (`finish_reason == "length"`), and an empty reply raises `AIGenerationError` ("The AI returned an empty reply…"). OpenRouter sometimes answers HTTP 200 with `{"error": {"code": 503, …}}` and no `choices` (e.g. a provider overloaded); the SDK doesn't raise for it, so `check_reply` raises the matching `openai.APIStatusError` (502 when the code is unusable), which gets the right `ai_failure` message and the flashcard retry rules. Every reply must go through `reply_text` or `check_reply`. Summary calls go through `_complete`, which retries temporary failures (overloaded, 429, 5xx, timeout, connection) up to `TRANSIENT_RETRIES` (2) times with a growing pause, because a map-reduce or merged summary makes several calls and one blip would fail them all; flashcards retry once. Output caps: `model_limits.py` loads the model's `context_length` and `max_completion_tokens` from OpenRouter's public model list once at start-up (`main.py`), and `cap_tokens()` caps every summary and flashcard `max_tokens` to it (4,096 when unknown, e.g. offline or in tests) - requesting more than a model allows fails the call (gpt-3.5-turbo allows 4,096; the reasoning allowance pushed requests past that). Long material: map calls (and condensing calls) run through `run_calls`, up to `SUMMARY_PARALLEL_CALLS` (4) at a time, results in order, first failure cancels the rest. If the map notes exceed `final_input_budget()` (from the model's context; 24,000 characters when unknown), `fit_notes` condenses them in rounds (groups of at most 12,000 characters, labels kept) until they fit, giving up after 4 rounds with `TOO_LONG_MESSAGE`; merged, cited and plain summaries all use it. Offline tests: `tests/test_model_limits.py`, `tests/test_summary_rounds.py`, `tests/test_parallel_calls.py`. OpenRouter's daily free-model cap (`is_daily_limit`: 50 requests a day on an account without credits, `limit_source: openrouter_free_tier_daily`) is never retried and gets `DAILY_LIMIT_MESSAGE`. Offline tests: `tests/test_reasoning_model_output.py`, `tests/test_error_in_reply_body.py`, `tests/test_summary_retries.py`. Each service (`search_service`, `ai/summary_service`, `ai/flashcard_service`) creates its own client. Summary and flashcard generation work on `Document.content` and split it into 3000-char chunks when it is over 6000 chars (summaries map-reduce; flashcards generate per chunk until `count` is reached), and raise `AIGenerationError`, which the routes turn into 502s. Its message is shown to the user as-is, so build it with `ai_failure(e, "...")` (`summary_service.py`): it logs the raw OpenRouter error and maps it to a plain sentence (402 out of credits, 401 bad key, 404 model unavailable, 429 rate limit, timeout, 5xx, …). Search does the same: `generate_answer` raises instead of returning an error string, and `/search` answers 502. The summary and flashcard routes can be hit twice at once (the pages auto-generate when nothing exists, and React StrictMode runs that effect twice in dev), so they take `_lock_document` (a row lock) only around the save, never the LLM call, and re-read before writing; the frontend also shares an in-flight generation request per document (`shareInFlight` in `api/client.ts`).
- **Search** (`GET /api/v1/search?query=`) returns `{query, answer, top_matches[{score, content, document, youtube_timestamp_url, source_type, source_url, location}]}` built from the top 3 Chroma hits (`location`: "02:05" for YouTube, "p. 12" for PDFs with pages, else null).
- **Rename** (`PATCH /api/v1/documents/{id} {filename}`): search results take the name from Chroma metadata, so `rename_document` rewrites `filename` on the document's vectors first, then commits the row, and puts the old metadata back if the commit fails. Whitespace is collapsed; empty or over 255 characters → 400. Summaries already generated keep whatever name they were built with (only website summaries embed it, in the `Source:` footer). Offline tests: `tests/test_document_rename.py`.

## Frontend architecture

- All HTTP goes through `src/api/client.ts` (relative `/api` base, relying on the Vite proxy); response types are in `src/types/index.ts` and mirror the backend dicts by hand, so update both together.
- Routes are defined in `src/App.tsx`: `/login`, `/signup`, `/forgot-password` and `/reset-password` are public; everything else is under `RequireAuth` > `AppLayout` (sidebar + `<Outlet/>`): `/`, `/library`, `/library/:documentId/summary`, `/library/:documentId/flashcards`, `/library/merged/:setId/summary`, `/library/merged/:setId/flashcards` (the same two pages with `merged`), `/library/:documentId/quiz`, `/library/merged/:setId/quiz`, `/flashcards`, `/review` (Due today), `/settings`. `ChatPage` exists but is not routed. Every page except `HomePage` is `lazy()`-loaded (in-app pages wait in AppLayout's `Suspense`, so the sidebar stays; public pages use `PageFallback`), and `vite.config.ts` puts React, react-dom and the router in a `react-vendor` chunk (Rolldown `codeSplitting.groups`); add new pages the same way. Source-type icons and colours come from `components/library/sourceBadge.tsx` (DocumentCard and the Flashcards hub's document cards still have their own copies).
- `DocumentContext` holds the shared document list for the Sidebar and Home. `SplashScreen` seeds it on first load. `LibraryPage` keeps its own separate fetched copy.
- Styling mixes CSS variables from `src/styles/design-tokens.css` with many hard-coded hex values in Tailwind arbitrary classes.
